# Runtime and installation specification

Status: implementation contract, 23 September 2026. This document specifies work for Claude; it does not report a working Cloudflare deployment. Read it with the storage/jobs specifications and [verification and cutover](04-verification-and-cutover.md). Requirement IDs identify reviewable acceptance conditions.

## Runtime selection and packaging

**RT-01 — Central capability selection.** Add `DEPLOYMENT_TARGET=node|cloudflare`, defaulting to `node` when absent so existing installations retain their behavior. Resolve it alongside the existing `DEPLOYMENT_MODE` and `AI_TRANSPORT` in one server-only module. Derive the backend from this supported matrix; do not introduce a separately configurable backend selector.

| Target | Mode | Storage | Transport |
| --- | --- | --- | --- |
| `node` | `standalone` | Existing Redis | `direct` or `gateway` |
| `node` | `hosted` | Platform Redis and researcher BYOS Redis | `direct` |
| `cloudflare` | `standalone` | Workspace SQLite DO | `direct` or `cloudflare-gateway` |

`gateway` (Vercel AI Gateway) remains Node-only; `cloudflare-gateway` is Cloudflare-only. Either mismatch fails setup/readiness before storage or provider use.

Unknown values and unsupported combinations fail setup/readiness and affected requests before storage or provider use. The custom Worker entrypoint additionally requires its declared target to be `cloudflare`; the backward-compatible missing-value Node default must not activate a Redis path inside a Worker. Never infer target from request headers, available credentials, or a failed backend connection. Preserve the keyless `/demo`. Keep Workers-only imports out of the Node module graph; choose backend factories at the runtime boundary rather than branching throughout routes.

**RT-02 — One Worker artifact.** Use a custom Worker entrypoint which delegates `fetch` to OpenNext, implements an independent `queue(batch, env, ctx)` handler, and exports the `WorkspaceStore` class. Declare binding `WORKSPACE_STORE`, producer `ANALYSIS_QUEUE`, its consumer, and the SQLite class migration in Wrangler configuration. Preserve any generated OpenNext exports required by the selected cache configuration. Queue delivery must not call the public HTTP analyze endpoint or depend on a Next request context. The DO owns transactions, outbox and alarms; the queue handler owns provider execution. [OpenNext custom entrypoints](https://opennext.js.org/cloudflare/howtos/custom-worker).

Add `open-next.config.ts`, `wrangler.jsonc`, the custom entrypoint, generated binding types and focused Cloudflare test configuration. `ASSETS` points at the adapter's generated assets; retain any required self-reference binding with the actual installation's Worker name. Ignore `.open-next/`, `.wrangler/` and secret-bearing local configuration. Avoid adding R2, image services or a second Worker unless an observed application requirement justifies them.

**RT-03 — Locked feasibility gate.** Start in an isolated checkout with Node 24.19+ and `npm ci`. Preserve locked Next 16.3.4/React 19.3.0 initially. Select mutually compatible exact OpenNext, Wrangler and Workers test-tool versions, commit the resulting lockfile, and record the tested compatibility date/flags in configuration. Do not run an unpinned migration generator against an authenticated account. Retain explicit `nodejs_compat` where accepted by the pinned toolchain; prove required crypto, Buffer, streams and SDK behavior in workerd. Runtime compatibility is not established by a successful Node build. [OpenNext setup](https://opennext.js.org/cloudflare/get-started).

The first deliverable proves generated production fetch, protected-page proxy, cookie signing/verification, a transactional toy DO and a Queue fixture in one artifact. Record artifact size/startup evidence and exact dependency versions. If proxy/auth or composition fails, provide the reproduction and a bounded alternative decision before the broad storage conversion; do not silently rewrite the framework.

**RT-04 — Commands and artifacts.** Preserve `build`, `start` and existing Node checks. Add `build:cloudflare`, `preview:cloudflare` (local workerd), `test:cloudflare`, `typegen:cloudflare`, `setup:cloudflare` and `deploy:cloudflare` commands, using installed binaries. Build must never provision or deploy. Deploy consumes a previously checked artifact/configuration; it must not rebuild unrelated source after approval. Publish a non-secret manifest containing commit, lockfile/artifact/config hashes, schema compatibility range and test receipt. Exact filenames may follow repository conventions; command responsibilities may not blur.

## Configuration, authority and runtime behavior

**RT-05 — Runtime bindings and secrets.** Construct a validated runtime context from Worker `env` for HTTP, Queue and alarm execution. Pass selected provider keys explicitly to existing adapters; never copy `env` into mutable global `process.env`, depend on a preceding HTTP invocation, or embed secrets at build time. Where existing Next code still reads deployment-wide `process.env`, verify adapter/compatibility behavior and move unsafe access behind the context resolver. Workers can populate environment values, but mutation persists within the isolate; it is not per-request configuration. [Workers process behavior](https://developers.cloudflare.com/workers/runtime-apis/nodejs/process/).

Study provider/model selection and served-model provenance remain authoritative. A missing study-selected provider key is a configuration failure, never a fallback to another provider. Retain native key names. Any subset of the four native keys may be bound; `AI_PROVIDER` names the installation default, whose key is required. On Cloudflare, adapters receive explicit endpoints and never read SDK environment defaults (owner amendment, 24 September 2026). `ANALYSIS_RECOVERY_EPOCH` is non-secret external deployment configuration governed by the jobs/restore protocol; never regenerate it during a normal update.

**RT-06 — Auth and origin.** Preserve the researcher/participant audiences, cookie names, independent signing secrets, expiry and participant tab selector. Test `src/proxy.ts` in the actual artifact: protected pages redirect, invalid cookies clear, and API handlers independently enforce authority. `APP_BASE_URL` remains an explicit stable HTTPS origin in production; reject credentials, paths, query strings, fragments and localhost. A `workers.dev` origin is valid. Neither Host, XFF, `VERCEL_URL` nor the first request may establish it. Keep private responses and participant exchanges out of shared caches; static-asset routing must not bypass protected pages or APIs.

**RT-07 — Client identity.** Establish a typed, server-owned admission identity at the custom fetch boundary and convey it through the adapter without trusting a browser-provided internal header. Strip/overwrite any such header; prove it survives Next proxy/reconstruction. Cloudflare ingress uses only the validated `CF-Connecting-IP`, never Vercel, XFF or `x-real-ip` fallbacks. Normalize IPv4 and equivalent IPv6 spellings before HMAC; reject address lists, ports, zone suffixes and malformed values. Retain full normalized IPv6 rather than introducing a new subnet policy. Disable Pseudo IPv4 overwrite for supported installations and test the resulting header behavior. Missing/invalid identity enters one salted `unknown` client bucket per existing scope, never an unlimited path; emit a bounded diagnostic without the address.

External Worker subrequests are not supported for participant paid/save endpoints initially: conservatively reject subrequest-marked traffic before provider use. Never use a caller-selected `CF-Worker` string as a budget key or grant it trust. Cross-zone requests can carry a fixed Cloudflare address; same-zone Workers can affect the apparent client address. Validate this policy against real ingress in staging and prove OpenNext self-reference does not internally forward these mutations. If reliable classification is unavailable, retain a conservative shared subrequest bucket and document the limitation; do not claim user-IP attribution. Independent session/link/study/researcher limits remain mandatory. Preserve Node behavior behind its own identity adapter. [Cloudflare header contracts](https://developers.cloudflare.com/fundamentals/reference/http-headers/).

**RT-08 — Readiness.** Extend the existing setup checker and `hostedConfig` capability checks together. Cloudflare requires valid configuration, independent secrets, the default provider's key, well-formed values for every bound key and, when `cloudflare-gateway` is selected, the gateway identifiers and an independent gateway token; SDK override variables are refused (owner amendment, 24 September 2026). It also requires `WORKSPACE_STORE`, `ANALYSIS_QUEUE` and supported schema; it must neither require Redis nor construct a Redis client. Missing bindings, unsupported schema or a bounded DO readiness failure return not-ready/503. Public diagnostics expose only safe capability values, booleans and allowlisted reason codes. Add `analysisExecution: 'synchronous' | 'queued-v2' | null` to `PublicConfigView` and `/api/config/readiness`: valid Node uses synchronous, valid Cloudflare uses queued-v2, invalid capability resolution uses null. Older deployments omit the field; clients treat absence as legacy synchronous and do not call a Cloudflare-only status endpoint. This advertisement does not authorize a request or override `ready: false`. Readiness must not call providers, dispatch jobs or write fixture records. Binding presence does not prove Queue consumption; installation verification tests that separately. Preserve existing Node readiness contracts.

**RT-09 — Complete route coverage.** Apply the domain boundary to every storage-using standalone route, including demo seed, study mutation, participant links/consent, interview lists/details/export, aggregate storage and follow-up generation. Preserve their authentication and revision checks. Greeting/interview, aggregate and follow-up provider work may remain connected HTTP operations with explicit deadlines. The post-response 30-second limit is not a connected-request deadline. Deferred interview analysis moves to the durable job path. [Invocation limits](https://developers.cloudflare.com/workers/platform/limits/).

Bound aggregate inputs and export reads; the current server-side JSZip export materializes up to 500 interviews. Demonstrate accepted maximum inputs within Worker memory/CPU, or implement bounded streaming/pagination while preserving the download contract. Never silently truncate a successful export. Storage and cutover specifications define snapshot/backup consistency; an interview ZIP is not an operational backup.

**RT-11 — Cloudflare AI Gateway transport** (owner amendment, 24 September 2026). With `AI_TRANSPORT=cloudflare-gateway`, the native adapters send each provider request to `https://gateway.ai.cloudflare.com/v1/{CF_AI_GATEWAY_ACCOUNT_ID}/{CF_AI_GATEWAY_ID}/{google-ai-studio|anthropic|openai|openrouter}` and nowhere else. Code builds the URL from validated identifiers; no configurable URL exists, and SDK environment overrides (base URLs, custom headers, auth tokens, logging, Vertex selection) are refused. Every request carries exactly `cf-aig-authorization`, `cf-aig-collect-log: false`, `cf-aig-collect-log-payload: false`, `cf-aig-skip-cache: true`, `cf-aig-max-attempts: 1` and `cf-aig-no-wholesale: true`. The native key travels on each request; stored gateway keys and Unified Billing are not used. The unified, universal, REST and dynamic-route endpoints and the `ai` binding are not used, so the gateway adds no fallback. The gateway is created with authentication, logs off, caching off, no retries, `byok_only`, and no DLP, Guardrails, Logpush or OTel. Queued synthesis keeps its no-SDK-retry policy. Provenance keeps the provider-reported model and the native requested model and records `aiTransport: cloudflare-gateway`. Gateway rejections before the provider are known failures; timeouts, 5xx and unrecognized outcomes after the start marker remain uncertain and are never repeated automatically. A missing or malformed gateway configuration is a configuration failure, never a fallback to direct. The transport disclosed at consent is recorded with the consent, interview and frozen analysis input; a provider call carrying participant content runs only when the current route is direct or equals the disclosed route. AI Gateway is incompatible with Cloudflare Regional Services, so `WORKSPACE_JURISDICTION` governs Durable Object storage only, and the participant disclosure says so.

**RT-10 — Logs.** Preserve structured allowlists and corrupt-record diagnosis. Log operation, bounded failure reason and status, never request bodies, SDK error objects, credentials, participant codes or research content. Review Workers automatic invocation logs/traces before enabling them: raw `/p/<token>` URLs are sensitive even if application logs are clean. Disable URL-bearing automatic capture where it cannot be redacted, retaining safe application events. Include harmless marker tests across runtime error/reporting paths; no broad observability redesign is required. [Workers Logs](https://developers.cloudflare.com/workers/observability/logs/workers-logs/).

## Repeatable installation and updates

**SETUP-01 — Checked-in installer.** `setup:cloudflare` provides `plan`, `apply`, `resume`, `verify` and `update` operations backed by deterministic scripts, not instructions for an agent to improvise. Inputs include account, install name, environment, provider, explicit origin or authenticated origin discovery, and install/update intent. The read-only plan lists resources and changes. Require an explicit existing-install identity for updates; refuse ambiguous name collisions. Save a non-secret installation receipt with account/resource identifiers, completed phases and deployed version. No production IDs belong in generic templates.

Resource names are derived once, validated and reused: Worker, namespace/class binding, analysis Queue and any recovery queue required by the jobs spec. Bind producer and consumer to the same selected queue. Interrupted setup resumes from observed resource state; it does not create duplicates or delete partially created resources automatically. Preserve existing secrets, origin, epoch and data on replay/update. Unexpected drift stops with an actionable diff. Secrets arrive via protected input/stdin or authorized secret manager, never CLI arguments, logs or committed files.

**SETUP-02 — Credentials.** Fresh installation generates three independent cryptographically random 32-byte signing/salt values for `SESSION_SECRET`, `PARTICIPANT_TOKEN_SECRET` and `RATE_LIMIT_SALT`; the administrator supplies or securely receives an independent password meeting the existing 16-character minimum. Do not print generated credentials into build output. Require the default provider's native key; the operator may bind any of the four at install and add or rotate keys later through explicit update operations that upload only the named secret. Generated secrets and the epoch are never rotated by the installer (owner amendment, 24 September 2026). No Upstash account, hosted OAuth or encryption keyring is needed. Reject blank/template/reused credentials. Explain Workers and provider billing before apply; existing account allowances are not assumed unused.

**SETUP-03 — Origin bootstrap.** Prefer a user-confirmed final HTTPS origin. Otherwise the authenticated installer obtains the actual account subdomain/Worker deployment URL, verifies ownership/name, and sets `APP_BASE_URL`. If the URL exists only after deployment, initial configuration remains not-ready with participant/researcher mutations closed; complete a second configuration deployment before success. Origin bootstrap cannot use an anonymous setup endpoint. Custom-domain routing is an explicit later operation; changing origin does not silently rotate secrets or claim existing sessions migrate.

**SETUP-04 — Deploy button.** Deliver README and `/self-host` instructions plus a tested Deploy to Cloudflare link. The public source repository must be self-contained; a subdirectory template cannot depend on files outside that directory. Supported provisioning includes DOs and Queues, but secret discovery reads `.dev.vars.example`/`.env.example` and custom commands must be configured deliberately. [Deploy button documentation](https://developers.cloudflare.com/workers/platform/deploy-buttons/). The Deploy button template remains direct-transport with one provider key.

Provide a Cloudflare-specific template/example and binding descriptions. Prove how the template exposes only the selected provider's key without requesting Redis, all four keys or hosted fields. Test secret-example precedence and renamed resources. If native conditional selection is unavailable, offer a clearly labeled tested provider-specific template or the guided installer; do not invent unsupported dashboard behavior. Similarly, if origin bootstrap or required release gates cannot run in Workers Builds, describe the required guided completion and leave the app not-ready. Publish a one-button-ready claim only after the complete empty-account-resource journey passes.

**SETUP-05 — One deployment owner.** Project production uses a GitHub Actions promotion job dependent on the full required matrix for the exact source/artifact. Disable competing push-triggered Workers Builds deployment. For button installations, choose either the same CI owner or a tested Workers Builds pipeline whose deploy command runs the complete prescribed predeploy gate first. Independent GitHub checks do not gate a Workers Builds push. If that environment cannot execute the required checks, require CI onboarding before enabling automatic updates; do not weaken tests. Updates preserve the installation receipt/configuration and use compatibility rules in [verification and cutover](04-verification-and-cutover.md). [Builds behavior](https://developers.cloudflare.com/workers/ci-cd/builds/).

Disable production Version URLs and branch Previews initially. Full workflow staging uses a separately named Worker, isolated DO namespace, Queue, secrets and origin. Branch Previews can isolate same-Worker DO state, but named Queue producers may share resources and Previews currently cannot consume Queues. A version upload is also not storage isolation. [Preview resources](https://developers.cloudflare.com/workers/previews/resources/).

**SETUP-06 — Agent skill deliverable.** Claude should eventually ship a repository skill plus supporting installer documentation, not a second deployment implementation. The skill identifies install/update intent and target, runs the checked-in plan, uses existing session authorization, obtains required credential authorization, applies/resumes the reviewed plan, and runs verify. It must obey repository 1Password rules, never enumerate credentials, delete old infrastructure, change DNS, or perform paid smokes implicitly. Its successful handoff reports canonical URL, version, resource receipt and verification limitations. The present specification is not that runnable skill.

**SETUP-07 — Acceptance receipt.** Demonstrate fresh renamed installation, synthetic authenticated save → Queue analysis → export, no Redis traffic, clean repeated apply/update, interrupted-install recovery, missing-binding/origin failures, and a deliberately failed release check leaving production unchanged. Record manual dashboard steps honestly. No live-provider success is inferred from fixtures; authorized provider smoke and cutover remain separate gates in specification 04.

**SETUP-08 — Gateway provisioning** (owner amendment, 24 September 2026). For `cloudflare-gateway`, the installer creates a per-installation gateway (id = Worker name; staging separate) through the Cloudflare API with an operator-supplied management token held only in process memory, adopts one only on recorded-attempt evidence, never uses `default`, and never deletes a gateway. The runtime AI Gateway Run token arrives through protected input and is probed without a provider call. `verify` compares gateway settings and confirms zero stored logs when a read-capable token is available and otherwise states the limitation.
