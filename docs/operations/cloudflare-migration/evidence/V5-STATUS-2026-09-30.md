## What the 18 studies and 15 interviews mean

These counts belong to the maintainer's **synthetic staging acceptance corpus**,
created on 24 September, then imported into a separately isolated restore
installation. They are not another researcher's corpus, the contributor's fork
data, or a production inventory. The 15 historical analysis jobs comprised
eight completed and seven failed tests; none was active at the drill's start.
Earlier acceptance tests used real provider calls with invented inputs. The
later recovery drill made none.

These records were created through ordinary application workflows, not the
designated **Load Sample** seed, so **Clear Sample** is not their cleanup tool.
The two new recovery-drill studies were deleted; the original research families
were preserved. The isolated installation remains held in `recovery`, with its
epoch matching and no active jobs, as observed at drill completion. Its Worker,
storage, Queue and protected evidence are retained; no infrastructure deletion
has been performed.

Counts in a backup are a snapshot. Check the intended installation and record
provenance before drawing conclusions about users or deleting anything.

## How to resume

1. Inspect current source, Git status and runtime readiness; this note can age.
2. Use [INSTALLER.md](../INSTALLER.md) and [RUNBOOK.md](../RUNBOOK.md), with one
   deployment owner and the exact checked release artifact. A readiness check
   does not authorize a restore, deployment or new provider call.
3. For a follow-up, name the isolated target, acceptance criterion, data and
   spending boundaries before execution. Preserve real production backups;
   never turn them into test fixtures or a second writable installation.
4. Store credentials, backup chunks, detailed receipts and local operator
   handoffs outside Git. Publish only content-free dated evidence, and update
   this index when a follow-up actually completes.

The repository guide and environment template already describe v5's current
contracts; this reconciliation adds no environment variables, services or
credential requirements.
