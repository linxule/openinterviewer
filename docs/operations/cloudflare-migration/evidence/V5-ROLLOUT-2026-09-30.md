## Backup, isolated restore and migration

Version 5 is **forward-fix**, not an in-place v4 rollback: migration 2 declares `minReaderVersion: 2`. The pre-upgrade backups were exported with the operator CLI matching the deployed schema-1 release, `c297750`, while each workspace was frozen.

- Staging backup: format 1/schema 1, 18 studies and 15 interviews. A fresh, separately named `--import-target` installation accepted all seven chunks and finalized the import. Recovery activation reconciled zero unfinished jobs. Its format-2/schema-2 re-export has identical counts and chunk checksums for all 11 non-workspace legacy families, including the original absolute expiry values. Workspace metadata differs intentionally: the target retains its own identity, maintenance state and activated epoch.
- The isolated restore installation remains in `recovery`, with the activated epoch matching, no scheduled alarm and no provider execution. It is retained for recovery verification; no infrastructure was deleted.
- The later staging format-2 backup includes the synthetic acceptance interview and both saved notebook answers. The researcher ZIP export also contains that interview and both answer JSON files.
- Production's complete pre-upgrade backup has one study, one interview, its analysis/job and link, with zero active consents or unfinished jobs. After the installer update, schema 2 reports those same legacy-family counts and an empty notebook. The recovery epoch fingerprint is unchanged on both maintained environments.
- The new backup reader independently validated the manifests, every chunk checksum, closed family shapes and completion trailers of all four backup directories. Backups and detailed receipts remain private outside Git; no production participant content was used as a test fixture or copied into this document.

The installer returned exit 3 after each successful update because the workspace was intentionally frozen. Each workspace was reopened by a compare-and-set maintenance transition, then `verify` passed on both workers.dev and the canonical origin. A receipt's `lastVerification` can still describe the held state immediately after deployment: the subsequent read-only `verify` does not rewrite that installation receipt. The private rollout receipt records the final ready checks.

Both notebook scopes selected exactly the intended interview with an explicit age 20–29 filter. A same-key exploration replay returned the original saved OpenAI answer. Pausing and resuming collection did not advance the study revision; the real configuration edit advanced it from 1 to 2. The canonical-origin participant session and gateway consent disclosure were exercised. Greeting and interview-turn calls were deliberately omitted to stay inside the three-call approval.

Saved answers and quote-location controls rendered at desktop and 375-pixel width without horizontal overflow. Study settings downloaded a valid ZIP containing the interview and both notebook answers. The Danger Zone's first confirmation, second confirmation and required acknowledgment were exercised before deleting only this synthetic study. Afterwards the study, interview, notebook and scoped export returned 404, and aggregate lookup returned null. The pre-existing staging study and interview counts remained 18 and 15. Identifier-only deletion fences and receipts may remain; live research artifacts do not.

No provider call was made against production during this rollout. Existing studies retain their configured model choices; the new OpenAI and Claude defaults do not silently rewrite collected-study configurations.

## Post-rollout development-toolchain hardening

The follow-up publication surfaced GitHub security alerts for the development-only Miniflare dependency on Undici 7.29.0. The production dependency audit was already clean. A scoped npm override selects Undici 7.29.1 only under Miniflare, the patched version named in the [upstream security advisory](https://github.com/nodejs/undici/security/advisories/GHSA-w293-vg96-wgc3). The lockfile changes only that nested package's version, resolved URL and integrity; the Wrangler, Vitest plugin, Miniflare and workerd pins stay unchanged. Remove or revisit the override when the pinned toolchain itself selects a patched version.

This is a development-toolchain follow-up, not a redeploy, new application release or a change to the v5.0.0 tag. It does not imply that the original rollout used the overridden dependency. Its compatibility checks belong to the follow-up PR, separately from the release-artifact receipt above.

CI now audits the entire dependency graph at high severity, and the local release check adds an `audit-toolchain` lane alongside its production audit. Both explicitly include development dependencies, even under inherited production/omit settings. A realistic CLI regression makes the fixture production audit pass while the development audit fails, and requires a failed release receipt in default, production, omit-dev and combined environments. This closes the production-only audit blind spot without weakening the existing gate.
