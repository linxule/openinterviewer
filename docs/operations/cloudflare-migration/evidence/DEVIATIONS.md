# Deviations and implementation decisions

Every place the implementation departs from, tightens, or decides something the specification left open. Each entry gives the requirement, what was done, and why. Items marked **tightening** are stricter than the specification; **decision** fills a gap the specification left open; **deviation** differs from the specification's literal wording and needs reviewer attention.

| SETUP-02 (key removal) | decision | `update --forget-provider-key <p[,p…]>` (design C) records a removal the operator made by hand: the installer never deletes a secret. | F5 (sign-in budget) | tightening | On Cloudflare, `POST /api/auth` streams at most 1 KiB of body, then admits the attempt atomically before comparing the password (`admitLoginAttempt`, one transaction: refuse if either window is full, otherwise count in both). The windows are 10 attempts per client key per 15 minutes (HMAC of the normalized IPv4 address or the IPv6 /64, or the shared `unknown`/`subrequest` scope) and 200 across all clients per hour. They are fixed windows, opened by the first counted attempt and never extended, and use the Worker's clock. An attempt refused by either window counts in neither, so a client already refused never charges the global window. A correct password calls `refundLoginAttempt`; a lost refund leaves the attempt counted, and sign-in still succeeds. Limited → 429 with `Retry-After`; budget unavailable → 503. Sign-in answers under maintenance, epoch, identity and uninitialized holds (only an unsupported schema refuses). `login_attempts` lives in the unreleased migration 1 and is excluded from operational backups and the research mutation sequence | The specification has no sign-in limit; the admin password is the only researcher credential. A check-then-record pair let concurrent guesses pass one check; atomic admission bounds each window exactly. Operators must be able to sign in to a held workspace, and sign-in attempts must not move a frozen workspace's backup watermark. |
