# Deviations and implementation decisions

Every place the implementation departs from, tightens, or decides something the specification left open. Each entry gives the requirement, what was done, and why. Items marked **tightening** are stricter than the specification; **decision** fills a gap the specification left open; **deviation** differs from the specification's literal wording and needs reviewer attention.

## Runtime and configuration

| Ref | Kind | What | Why |
| --- | --- | --- | --- |
| RT-03 | decision | `@cloudflare/vitest-plugin` 1.2.3 replaces `@cloudflare/vitest-pool-workers` 0.22.0; compatibility date 2026-09-15 | The pool package was renamed; 0.22.0 pins an older workerd that rejects dates after 2026-08-22. The plugin pins the same wrangler/workerd as production, so tests and the artifact share one runtime. |
| RT-05 | deviation (wording) | "Never copy env into process.env" is read as: application code never writes `process.env` and never uses it as Cloudflare authority | The platform (`nodejs_compat_populate_process_env`) and OpenNext already populate `process.env` with string bindings; M0 proved presence in fetch, alarm and Queue handlers. Bindings and provider keys for Cloudflare paths come from the invocation env. |
| RT-01/RT-06 | tightening | Cloudflare validation is production-strict regardless of runtime `NODE_ENV` | `NODE_ENV` is undefined at runtime in the Worker for aliased reads; relying on it would treat a Worker as development. |
| RT-06 | tightening (Node change) | Node production now rejects every loopback `APP_BASE_URL` spelling (127/8, `[::1]`, IPv4-mapped loopback, `localhost.`) | The previous `::1` check was dead code (WHATWG keeps brackets). Only Node production loopback origins are affected. |
| RT-08 | decision | `/api/health/ready` reports not-ready (`workspace_maintenance`) while the workspace is `draining`, `frozen` or `recovery` | The workspace refuses new collection or research writes in those states. Administrator sign-in does not depend on readiness. |
| RT-08 | decision | A readiness request may complete a deployment-configured bootstrap (schema migrations and workspace metadata when `WORKSPACE_BOOTSTRAP` is set) | Any first access to a fresh object runs migrations; initialization happens only under the installer's explicit bootstrap value and never writes research or fixture records. |
| RT-08 | decision | Missing `OPERATOR_TOKEN` is a setup warning, not a readiness error | Readiness gates participant and researcher routes; the operator routes fail closed on their own without the token. |
| RT-10 | tightening | Setup checker errors on `logpush` or tail consumers | Both forward per-invocation request metadata including URLs (participant codes). |
| RT-02 | decision | `WORKER_SELF_REFERENCE` is not bound | With the dummy cache configuration and the App Router it is unused; dropping it removes a rename hazard for installations. |
| F2 | tightening | A fresh Durable Object initializes only under `WORKSPACE_BOOTSTRAP=open\|recovery`. `deploy.mjs` accepts those values only with `--bootstrap`, which the installer passes for its initial, origin and workspace-init deploys, and refuses any other non-empty value. The installer refuses any other deploy while its receipt lacks `workspace-init` | Prevents identity, jurisdiction or Worker-name drift from silently creating an empty writable workspace, including through a copied bootstrap config deployed outside the installer (the CI promotion). |
| F4 | tightening | `ANALYSIS_RECOVERY_EPOCH` is a secret binding | A var would roll back with no warning at all. Across a modified secret, `wrangler rollback` lists the secret and asks for confirmation (API code 10220). That prompt is a warning, not a guard: it defaults to yes, and wrangler answers it yes by itself without a TTY or in CI (4.136.3: `confirm2` returns its fallback value, yes, when `isNonInteractiveOrCI()`). The RUNBOOK therefore forbids any rollback between an epoch rotation and its activation, re-checks `epoch.configuredMatches` after the restore, and allows a native rollback only interactively (OPS-03). |
| RT-02 / ST-08 | deviation (platform) | The OpenNext server wrapper is overridden with `cloudflare/opennext/backpressureWrapper.ts`, a copy of `@opennextjs/aws` 4.1.4 `cloudflare-node` with two changes: response writes are acknowledged only while the Response body queue is below 256 KiB (released on pull), and an error on the piped source errors the body. `@opennextjs/cloudflare` validates the wrapper by name, so `dangerousDisableConfigValidation` is set; `tests/unit/openNextConfig.test.ts` re-asserts every other field and pins the upstream file's SHA-256 | Upstream acknowledges every write immediately, so a streamed export was drained into the 128 MB isolate at production speed regardless of the client, and a stream failure after the headers could end the body cleanly. Removes the need for an archive byte cap (only ZIP32 limits and the 500-interview ceiling remain). Upstream report recommended. |
| RT-04 | decision | `preview:cloudflare` runs the built artifact in local workerd through the browser-lane harness: synthetic OpenAI responses, fixed fixture credentials, every other outbound request refused, storage discarded on exit | A preview with real provider keys would be a paid path and would need secrets in a local file that `build:cloudflare` must refuse; the local preview's job is to show the exact artifact, not to call providers. |
| RT-04 / SETUP-03 | decision | `deploy.mjs` accepts an empty `APP_BASE_URL` only in a bootstrap configuration (`WORKSPACE_BOOTSTRAP` `open`/`recovery`), which in turn needs the installer's `--bootstrap`. `--check-config` validates an installation config alone (no artifact, nothing uploaded), and unknown options are refused | Lets the installer discover the `workers.dev` origin from the first deploy; without an origin the Worker is not-ready and refuses participant and researcher writes. |
| RT-04 (clean checkout) | tightening | A clean checkout means no uncommitted changes and no untracked file that `.gitignore` does not cover (`git status --porcelain --untracked-files=normal`, whatever `status.showUntrackedFiles` says). This applies to the build manifest's dirty flag, `check:cloudflare`, `deploy:cloudflare` and the installer. `build:cloudflare` no longer has `--skip-next-build` | An untracked file still goes into the Next build and so into the artifact, and a skipped Next build could label a stale `.next` as the current commit. |
| SETUP-04 | deviation (not delivered) | There is no Deploy to Cloudflare button, no button template, no `.dev.vars.example` and no binding descriptions. The guided installer (`setup:cloudflare`) is the supported self-host path, and the button stays unpublished, which `VERIFY-05` allows. The requirement stays open | The button clones the repository into the user's account and builds and deploys it with Workers Builds ([deploy buttons](https://developers.cloudflare.com/workers/platform/deploy-buttons/)). That conflicts with this implementation in three ways. (1) `SETUP-05` wants one deployment owner, and later pushes would deploy through Workers Builds, which GitHub checks do not gate. (2) The required gate, `check:cloudflare`, needs a local `redis-server` and Playwright browsers with system packages. The Workers Builds documentation describes no such build image, only a 20-minute build timeout, so it is not established that the gate can run there. (3) The origin and workspace bootstrap need the installer: it generates four secrets and the epoch, deploys with an empty origin and a bootstrap value, discovers the origin, initializes the workspace, then clears the bootstrap. A button runs one deploy command and asks the user to type every secret listed in `.dev.vars.example`. |
| SETUP-01 / SETUP-05 (CI promotion) | deviation | The maintained instance's deployment owner is the `promote-cloudflare` CI job. It deploys `vars.CLOUDFLARE_INSTALL_CONFIG`, the config that `setup:cloudflare config` writes from the receipt (local only, refused until the bootstrap is cleared). It never reads or updates the installer receipt, so the receipt's `deployments` and `verify --install`'s `Version` do not include CI deploys. It skips `update`'s receipt checks (queue ids, bound secret names, identity), and the variable must be regenerated with `config` and stored again after `update --change-provider` or a template var change. Before deploying, it checks the config (template drift, required vars, empty bootstrap); after deploying, it checks readiness at `APP_BASE_URL` (`setup:cloudflare verify --config`). A held workspace is a warning | The receipt is local, git-ignored state that a CI runner does not have. Keeping a receipt as repository state was out of scope. INSTALLER.md and the RUNBOOK ("Maintained instance: CI promotion") document the procedure and its limits. |
| F5 | tightening | Operator routes require a separate `OPERATOR_TOKEN` secret (constant-time) and a researcher session issued within 15 minutes | The specification names no operator credential; the admin password alone was judged too weak for restore/epoch activation. SETUP-02's "three generated secrets" becomes four. |
| F5 (operator holds) | decision | An operator 503 `WORKSPACE_HELD` carries the public `reason` plus the exact `holdReason` (`maintenance`, `schema-unsupported`, `workspace-identity-mismatch`, `workspace-uninitialized`, `recovery-epoch-mismatch`) | Only a caller that passed operator authority sees it, and the next recovery step depends on which hold it is. Public routes keep the two-value reason. |
| F10 (operator routes) | decision | Operator routes skip the deployment-readiness gate for the status and backup reads, backup import, recovery activation and transitions that tighten the hold (open → draining, any state → frozen or recovery). Transitions that resume work (to `open`, `frozen` → `draining`) pass it | A not-ready or held installation must stay diagnosable, exportable and restorable; import and activation act only inside the `recovery` hold, which the object enforces. Reopening a not-ready deployment stays impossible. |
| F5 / RT-07 (sign-in IPv6) | open question | The sign-in budget keys IPv6 by the full normalized address, as RT-07 requires ("Retain full normalized IPv6 rather than introducing a new subnet policy"). Residual risk: a host rotating addresses inside its /64 gets a fresh per-client window each time and is bounded only by the global window (200 per hour), which it can exhaust, blocking every sign-in, including an operator's, for up to an hour. Proposed adjustment for review (not implemented): key the sign-in budget only by /64. The same bound applies to an attacker with many IPv4 addresses | Implementing the subnet key would contradict RT-07's wording; the decision belongs to the reviewer. |
| F5 (password maximum) | tightening | `ADMIN_PASSWORD` has a maximum on Cloudflare. Its sign-in body `JSON.stringify({ password })` must fit in the 1,024-byte bound (`MAX_CLOUDFLARE_LOGIN_BODY_BYTES`, `src/lib/loginBody.ts`), which allows 1,009 ASCII characters and fewer with multi-byte or JSON-escaped characters. The installer refuses a longer password when reading it (`MAX_LOGIN_BODY_BYTES`, `scripts/cloudflare/installer/model.mjs`, the same value), and so does the operator CLI (`MAX_LOGIN_BODY_BYTES`, `scripts/cloudflare/operator.mjs`). `npm run setup:check -- --target cloudflare` reports it as `env.ADMIN_PASSWORD.too_long`, and readiness reports a longer bound value as `admin_password_too_long`. The Node target has no maximum. `tests/unit/adminPasswordLimit.test.ts` keeps all of these equal to `src/lib/loginBody.ts` | A longer password could never sign in, because the Worker refuses the body with 413. |
| F5 (Login form) | decision | The Login form sets no length limit on its password input, on any target, as before this work. On Cloudflare a password whose body is over 1 KiB gets 413 "Request body is too large", which the form shows | The form does not know the target, and Node has no body bound: a `maxLength` would cut a longer Node password short. The installer, the operator CLI, `setup:check --target cloudflare` and readiness enforce the Cloudflare maximum instead. |
| F5 (sign-in budget) | tightening | On Cloudflare, `POST /api/auth` streams at most 1 KiB of body, then admits the attempt atomically before comparing the password (`admitLoginAttempt`, one transaction: refuse if either window is full, otherwise count in both). The windows are 10 attempts per client key per 15 minutes (HMAC of the full normalized IPv4 or IPv6 address, or the shared `unknown`/`subrequest` scope) and 200 across all clients per hour. They are fixed windows, opened by the first counted attempt and never extended, and use the Worker's clock. An attempt refused by either window counts in neither, so a client already refused never charges the global window. A correct password calls `refundLoginAttempt`; a lost refund leaves the attempt counted, and sign-in still succeeds. Limited → 429 with `Retry-After`; budget unavailable → 503. Sign-in answers under maintenance, epoch, identity and uninitialized holds (only an unsupported schema refuses). `login_attempts` lives in the unreleased migration 1 and is excluded from operational backups and the research mutation sequence | The specification has no sign-in limit; the admin password is the only researcher credential. A check-then-record pair let concurrent guesses pass one check; atomic admission bounds each window exactly. Operators must be able to sign in to a held workspace, and sign-in attempts must not move a frozen workspace's backup watermark. |
| RT-06 (link creation) | deviation | `POST /api/generate-link` bounds its JSON body at 140,000 bytes (read with `readBoundedJsonObject`, 413 above it), not the planned 4 KiB | The route reads only `studyConfig.id`, but researcher clients cached from earlier releases post the whole saved `studyConfig`; a 4 KiB cap would break Generate link for them. Same bound as `/api/greeting` (every valid 128 KiB study config plus its wrapper). `StudyDetail.tsx` now sends `{ studyConfig: { id } }`; tighten to 4 KiB once cached clients have aged out (Pending). |
| OPS-01 (public hold responses) | decision | A held workspace is a no-store 503 with only a public `reason`: `maintenance` (draining/frozen/recovery, `retryable: true`) or `workspace-unavailable` (epoch, identity, uninitialized, schema; `retryable: false`; the copy names the operator on researcher routes and the researcher on participant routes). Two routes are retryable for every hold: save, because the browser keeps the transcript, and analyze, because every API-01 503 is retried with the same key and body. A participant route whose session context fails with 503 now also returns the resolver's `retryable` (additive on Node) | Internal hold reasons stay in the allowlisted log. Retryability follows whether waiting can clear the hold. |

## Storage

| Ref | Kind | What | Why |
| --- | --- | --- | --- |
| ST-06 | tightening | Durable save admission checks and charges in one transaction | Redis checks and charges in separate scripts and can overshoot under concurrency (verified); the Redis behavior is a documented residual. |
| ST (create) | tightening | Durable create-idempotency quota counts only unexpired (7-day) receipts; a deleted study's receipt becomes `key-consumed` | Redis's index is never pruned (the 101st keyed create fails forever) and replays a deleted study as created. |
| ST (delete) | tightening | A refused delete (study has interviews) has no side effects | Redis leaves an in-flight delete guard that blocks later saves and edits (verified defect, residual on Redis). |
| ST (links) | decision | Link quota: 1,000 unexpired, unrevoked links per workspace | Redis counted revoked and never-expiring links. |
| ST-03 | tightening | Durable completion re-checks link active/unexpired, study revision, links enabled and consent inside the transaction; consent recording refuses a missing study or superseded revision | Redis relies on route-level checks. |
| ST-02/03 | decision | Authority is checked before duplicate detection, so a replay of a committed save after revoke/edit/delete is refused (Redis parity) | The specification says both "returns its original result" and "never authorizes new writes after revocation"; parity with Redis was chosen. |
| ST-07 | decision | Sample clear refuses (409 `SAMPLE_HAS_PARTICIPANT_DATA`, Cloudflare only) when the fixture study holds participant interviews; clear cascades links, consents, aggregate and jobs; clear-written fences allow a later fixture seed | Clearing real participant data is never acceptable; fixed fixture ids would otherwise block re-seeding for 30 days. |
| ST-08 | decision | Cloudflare collections are keyset-paged inside the object (≤ 12 MiB per page) and assembled by the client. Pages are separate transactions: rows present throughout appear exactly once (Redis parity: SMEMBERS then separate reads) | Worker RPC serializes non-Latin-1 strings as UTF-16 against a 32 MiB limit; paging keeps each RPC bounded. |
| ST-08 (list bytes) | tightening | A Cloudflare interview list assembles at most 16 MiB of serialized interview bytes (`MAX_LIST_INTERVIEWS_BYTES`) besides the route's count maximum; more is `too-large` (413), never a truncated list. Node has no byte ceiling | 1,000 records at the 512,000-byte save cap are about 500 MB, far beyond a 128 MB isolate. Sizing follows the aggregate input evidence (RT-09 row); the workerd measurement is a remote gate (Pending). |
| ST-05 | decision | A malformed immutable record is skipped in collections (Redis parity); malformed analysis state fails the collection with 503 instead of misrepresenting it | Never show a wrong analysis state; never silently hide a transcript because of mutable-state corruption. |
| ST-03 | tightening | Completion binds the record to the verified session (`session-<id>`), link and consent, and freezes the object's stored study config and provider/model rather than the caller's | Store-boundary authority (02-storage.md). |
| ST (schema) | decision | Migration 1 adds `interviews.study_revision` (aggregate eligibility), `deletion_fences.sample_fixture` and `login_attempts` (sign-in budget) | Additive, unreleased. |
| ST-09 | decision | Reader compatibility is declared per migration (`min_reader_version`, default = the migration's own version). A build serves a newer database only when every migration it does not know declares it a compatible reader; tampered checksums and ledger gaps refuse | Makes the N−1 → N → N−1 rollback window explicit and testable instead of refusing every newer schema. Only additive changes older builds can ignore may lower the value. |
| ST-09 | decision | An alarm that fires while the object is held by a condition a redeploy clears re-arms itself hourly (`HELD_ALARM_RETRY_MS`, `cloudflare/workspace/context.ts`) instead of being consumed. Those conditions are an unreadable schema, an uninitialized workspace, and an identity mismatch, whether found when the object initializes or at the scheduler's gate after initialization (the deployment's `WORKSPACE_ID` changed). A recovery-epoch mismatch and a maintenance hold consume the alarm; see JOB-05 | A compatible redeploy or a corrected binding then resumes dispatch without waiting for a researcher request. An epoch mismatch ends only through controlled activation, and maintenance only through an operator transition, and both re-arm the scheduler themselves. |
| ST-08 | decision | The Cloudflare ZIP uses DEFLATE (streamed); Node's JSZip export uses STORE | Entry names, order and decompressed contents are identical (parity test); archive bytes differ. |
| ST-08 | decision (all targets) | The browser export client (`isCompleteZipArchive`) refuses any 200 download unless it ends in a comment-less ZIP end record whose central directory ends there and lists exactly the recorded entries. This applies on Node as well as Cloudflare | A stream that fails after the headers can still reach the client as a clean 200. Both writers emit those records last, after every entry (and on Cloudflare after the final snapshot check). JSZip output passes the check. |
| RT-09 (aggregate input) | decision | Cloudflare aggregate synthesis pages current-revision analyzed interviews (100 rows, 4 MiB per page) and assembles at most 16 MiB of serialized (UTF-8 JSON) interview bytes. Larger inputs get 413 `AGGREGATE_INPUT_TOO_LARGE`, never a truncated input | RT-09 requires bounded inputs. The evidence, recorded in `src/lib/ownedStudies.ts`, is a V8 heap proxy in Node over the real route path and prompt builder: live heap at the provider call is 1.4–1.9× the input bytes, so 16 MiB keeps one request under about a quarter of the 128 MB isolate that concurrent requests and the OpenNext baseline share. Peak memory in workerd on a deployed Worker is not measured: remote gate (Pending). |
| RT-09 (aggregate/follow-up count) | decision | On Cloudflare the aggregate and follow-up 413 fires when `study.interviewCount` exceeds 1,000 (every revision and analysis state, as the Node read of 1,000 records does), checked before any page is read, and again when more than 1,000 eligible records turn up while paging | Parity with Node's limit; the second check covers interviews saved during paging. Follow-up keeps only ids per page and stops once every aggregate source is seen, so it has no byte ceiling. |
| OPS-01 (aggregate) | decision | Aggregate synthesis is refused (503 `maintenance`) in `draining`, `frozen` and `recovery` before the provider is paid. Follow-up generation stays allowed in `open` and `draining` | The route-group instruction said to allow it while draining, but aggregate synthesis ends in the aggregate write, and OPS-01 and the RUNBOOK allow researcher mutations only while `open`. The route checks readiness first. The object then fences every input page by `purpose` (aggregate: open only; follow-up: open or draining), so a transition after that check still refuses before the provider is paid. A transition after the last page is caught by the aggregate write, which the object refuses outside `open`: the paid result is then returned unsaved (no `savedAt`). |
| ST-07 (sample seed) | deviation (Node behavior) | The sample seed and clear go through store operations. POST's collision check is now the fixture ids (Node previously refused on any `demo-`-prefixed study). POST checks storage readiness before provider configuration and reads the fixture study only when no provider is configured, which keeps 409 ahead of 503. A clear that may have partly run returns 503 `{retryable: true, reason: 'ambiguous'}` instead of a thrown 500, and the Redis clear also removes fixture aggregates | A caller-selected prefix must not decide what counts as the fixture (02-storage.md); an ambiguous clear must not look like a server error. |
| INT (study-scoped list, Node body drift) | deviation (Node behavior) | `GET /api/interviews?studyId=` answers its 413 with "This study has too much interview data to list at once." instead of "This interview list is too large to load at once. Narrow it by study.", on Node standalone and hosted BYOS alike. The status is unchanged, and the unscoped list and the hosted inspection keep the old text | The old text told a caller that had already scoped the list to one study to narrow it by study. No client or test matches either string; `storageService` classifies the 413 by status and shows the server's text. The route's header comment still says hosted is unchanged. |
| ST (create, Node body drift) | deviation (Node behavior) | Node standalone `POST /api/studies` now runs through `store.createStudy`, and three error bodies changed (statuses unchanged): a failed storage ping after begin returns `{retryable: true, reason: 'unavailable'}` instead of "Storage not configured. Connect Upstash Redis to enable persistence."; an unavailable atomic create loses `error: 'Failed to save study'`; a create cancelled during reconciliation returns "Study already exists" (409). On a durable store, the unavailable bodies of study PUT/DELETE and sample seed/clear are retryable "temporarily unavailable" messages; Node keeps its "Storage not configured" wording | `CreateStudyOutcome` collapses these outcomes into one `unavailable` and one `conflict`; restoring the old bodies would need phase-specific outcomes in the port. Hosted create keeps its bodies. |
| ST-08 / F1 | deviation | An export captures its ordered interview key set, each row's analysis state and each aggregate's digest (in the object's synchronous KV, keyed by capture sequence, 24 h TTL, at most 8 kept, excluded from backups). Pages reproduce the captured state; only deletion/replacement of captured content invalidates the export | 02-storage.md fences on a workspace-wide mutation sequence, which would invalidate every export while analysis jobs or saves run (livelock during active collection). Transcripts are immutable and syntheses write-once, so the captured projection is a coherent snapshot. |
| OPS-02 | tightening | Import is bound to the complete manifest digest (equal to the trailer's `manifestSha256`); each chunk must match its descriptor; import chunks and epoch activation advance the mutation sequence | Prevents mixing chunks from different backups and keeps held-state watermarks exact. |
| OPS-03 (restore entry point) | decision | Point-in-time restore is an operator command: `recovery restore` calls `POST /api/operator/recovery/restore`, which calls the `restoreToBookmark` RPC. The object checks everything before any point-in-time storage call. It requires `frozen` or `recovery` at the expected state and version, exactly one of a bookmark or a time within 30 days, and a bound epoch that is valid, differs from the activated one and was never activated there. It checks again after resolving the time. It then calls `onNextSessionRestoreBookmark`, replies with `bookmark` and `undoBookmark`, and restarts itself (`ctx.abort`) after the reply. It writes no audit row; the decision is logged as `operator.action` `restore.schedule` | The platform's PITR API exists only inside the object, and Cloudflare's documentation says to abort afterwards. Requiring a rotated epoch makes OPS-03's "new epoch before restore" enforceable rather than procedural. An audit row would be rewound by the restore itself. |
| OPS-01 / OPS-04 (old-writer barrier) | decision | The barrier for the old Vercel/Upstash deployment is a reset of the Upstash database password, which revokes both REST tokens. It is verified by old tokens refused; every old URL cut off (readiness reporting the storage check failed, or, for a release older than the readiness route, a refused study create); a deliberately late study create refused; and a second inventory that shows no write: nothing grew, and every decrease is in keys that had an expiry ([TRANSITION.md](../TRANSITION.md) §6) | Vercel deployments are immutable, and callbacks already running keep their environment. Only revoking the storage credential removes write authority from every old deployment, alias and copy at once. DNS or a code flag cannot. |
| OPS-02 | tightening | Import requires the workspace_meta chunk's activated epoch to differ from the deployment's epoch, keeps the destination identity and held state, and fails closed on any cross-row identity mismatch | Otherwise imported unfinished jobs could resume without the activation reconciliation. |

## Durable analysis

| Ref | Kind | What | Why |
| --- | --- | --- | --- |
| JOB-08 | tightening | Claim, start and finish use the object's own clock only; the caller's `now` is advisory | A caller clock (stale or ahead) must never change a lease (gap F14). |
| JOB-07 | tightening | The 24-hour pre-start cap is also enforced at claim and at the start marker (recorded as failed/storage) | A late delivery must not start work the scheduler would already have failed. |
| JOB-07 / F6 | decision | A delivered-but-unclaimed job is deferred by another watchdog interval without charging the dispatch budget when a consumer contacted the object since its last send or deferral (contact kept in the object's synchronous KV, outside backups) | With concurrency 1, healthy backlog is not loss; each deferral needs fresh contact, so a lost delivery is still recharged and resent. |
| JOB-06 / F13 | decision | Structurally corrupt due jobs are quarantined in memory (30 s doubling to 1 h, count-only telemetry), never written | A corrupt row is never patched and cannot starve the 25-row alarm batch. An object restart retries each once. |
| JOB-05 | decision | An alarm that fires under a recovery-epoch mismatch or a maintenance hold is consumed. It is re-armed by epoch activation, by a transition that resumes work (in the same transaction), or by the next job-capable RPC: a status read or a retry that finds active work re-arms a missing alarm when the job-settlement gate passes (no SQL write). An identity mismatch keeps an hourly wake-up instead (ST-09) | Restores the wake-up invariant after a held period without making an epoch- or maintenance-held scheduler wake itself. |
| API-02 | tightening | Only `completed` records are analysable (status/retry: not-found; claim: corrupt, no write) | Matches the Redis attach script. |
| JOB-03 | decision | HTTP 5xx after start is recovery-required (uncertain), not a known failure | The specification limits known failures to configuration, rate-limit, invalid-output and size rejections. |
| JOB-04 | tightening | A researcher retry whose acceptance-time study revision raced a concurrent edit returns `state-changed` | Avoids allocating against stale frozen inputs. |
| JOB-02 | decision | A missing provider key or an unsupported frozen model ends the generation as `failed/provider` with zero provider requests | JOB-02 requires a recorded coarse failure without a request. |
| JOB-02 | decision | Nonterminal analysis with no active job (restore/import) projects recovery-required; `not-scheduled` is reserved for generation-0 records with no job and no synthesis | Never let imported or restored uncertainty look schedulable. |
| JOB-06 | decision | Claims, watchdog transitions and terminal writes advance the research mutation sequence | Analysis status and attempts are exported content. |
| JOB-07 | decision | Cleanup: link grace 7 days, at most 100 rows per table per alarm, cleanup-only wake-ups at most hourly; the current generation's terminal job row is never pruned | Local constants; the specification bounds only terminal-detail retention. |
| API-04 | deviation (Node behavior) | On Node, a `busy` result now stops the researcher batch as awaiting | API-04 requires it; previously `busy` counted as progress. |
| UI-CF-04 | decision | The Cloudflare batch observes (GET) already-active work instead of POSTing it | Closes a race in which active work turns recovery-required and a POST at the same expected generation would start an unseen paid retry (gap F8). |
