# OpenInterviewer 5.4.0 — draft

## Device voice input

A fourth study voice mode, **On the participant’s computer (desktop Chrome
only)** (`device`), lets the participant's browser turn speech into text locally.
Like the other voice modes, text appears in the answer box for review and is
never sent automatically. Inspired by Yinghua's
([@8888oukaouka-spec](https://github.com/8888oukaouka-spec)) participant-microphone
idea in her fork, credited in [5.1.0](v5.1.0.md) and
[ACKNOWLEDGMENTS.md](../../ACKNOWLEDGMENTS.md); this local-only implementation is
not authored by her or imported from the fork.

- Desktop Chrome 139+ exposes local speech recognition. The microphone appears
  only if the selected language's local pack is available, downloadable or
  downloading. Phones, Safari, Firefox stable and unsupported devices show no
  microphone; participants type instead.
- The first press can ask the browser to install a speech pack (about 60 MB).
  A localized preparation note appears; typing and Send remain available. Once
  ready, press the microphone again to start (no surprise recording after a
  slow download).
- Every recognizer started in device mode has `processLocally = true`. There is
  no fallback to browser cloud dictation or installation transcription.
  `language-not-supported` and `service-not-allowed` disable the mic for that
  participant session, with a short localized note.
- Consent presents locality as the browser's promise, not ours: the browser
  turns speech into text on this computer and says the recording stays there;
  the study receives only the text the participant sends. OpenInterviewer cannot
  verify what the browser does internally. The submitted **text** still
  follows the study's usual AI interview and storage terms.
- Works with standalone and hosted studies without server transcription
  credentials, capability or readiness changes. `/api/transcribe` still accepts
  only `installation`. Changing voice mode advances the study revision and
  invalidates older participant authority. Markdown exports describe the mode
  offered at collection, not whether the microphone was used.

## Upgrade and rollback

No dependency, database schema, environment variable or binding changes.

**Do not roll back a collecting device-mode study to 5.3.** The actual 5.3
validator at `f3eb006` was exercised against `voiceInput: 'device'`: canonical
validation, creation and an unchanged update return `Invalid voice input
setting`. An explicit update to `off` is accepted. The older code paths map
these failures to:

- 400 on creation or an unchanged configuration save.
- 409 from participant-context resolution (review/resave required) and link
  generation (`STUDY_REQUIRES_RESAVE`).
- 503 if the canonical-study loader independently encounters the invalid config.

The refusal occurs before participant provider use or persistence. Nothing is
silently converted to cloud dictation or deleted. Before rollback, stop
collection and save affected studies as **Off** on 5.4; this advances revision,
so issue new links before resuming. Historical interviews retain `device` in
`collectionConfig`; 5.3's Markdown export omits the device voice line, and
operations that validate historical configurations can refuse those records.
Rolling forward is preferable if they need processing or accurate export.
Existing schema downgrade restrictions still apply.

language mapping, consent and server/config boundaries. They cannot prove real
browser locality or language-pack support.

- Manually verify all six languages in desktop Chrome, including a fresh pack
  install, offline recognition with an installed pack, denied microphone access,
  and continued typing during download. Check unavailable browsers and a 375px
  setup/participant layout.
- Chinese tag: desktop Chrome 155 reports `zh-CN` (and the five other tags) as
  downloadable for local processing; `SPEECH_TAGS` keeps `zh-CN`.
- Have the five new translations reviewed. They are drafts, not part of the
  earlier translations' review receipt.
